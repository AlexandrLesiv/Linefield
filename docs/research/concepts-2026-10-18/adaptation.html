Concepts study: Linefield design adaptation v1.2

Date: 2026-10-18. Revision: v1.2, official findings CS-DOC-001–038 and device findings CS-OBS-001–020. Designer: ui_ux_designer. Status: research/design proposal; no application implementation, design review approval, native verification or usability study is claimed. Starting project revision: fbcc30ca115d630d6c9e688b1525d3ee1dcc89d7; preserve the current uncommitted work. This document is the designer's assigned contribution to the lead's broader Concepts investigation. Only this file is owned by this assignment.

Recommendation and evidence boundary

Study Concepts as a complete drawing workflow, then adopt its useful hierarchy: get into a drawing quickly, keep the canvas available, make the active tool and its properties legible, and reveal precise controls on demand. Preserve Linefield's established gallery and motion. Do not translate Concepts' extensive inventory into Linefield's first preview.

The first implementation proposal should remain small: a host-rendered drawing shell with the approved Pen/Select inventory and width/color presentation. Real editable strokes, selection, autosave and recovery require separate Rust/Wasm integration and their existing contract gates. The owner's newer five-tool/three-property image direction is a useful visual study, but its extra tools, opacity and adjustable smoothing need a product-scope decision. Do not resolve that mismatch by quietly adding features or by shipping disabled placeholders.

Ranked whole-app priorities from this study:

  1. Preserve the gallery and its transitions; make pending/failed persistence truthful before introducing richer organization. A saving overlay alone is not evidence of durability.
  2. Adapt compact tool/property access with explicit target scope and dismissal. Prioritize accidental-mark prevention, readable accepted values and keyboard/AX access over wheel styling.
  3. Keep one-stroke correction direct and predictable. Defer selection restyling, layers and precision features rather than silently changing what a shared property control edits.
  4. Keep color discoverable through native macOS controls and a separately reviewed web design; distinguish artwork color/opacity from translucent UI and keep host input differences visible.
  5. Make export stages explicit: generating a preview is not saving to a chosen destination. Defer Concepts' wider formats, library, accounts and sync; retain Linefield's recovery policy.

Outside press and property scope: explicit proposed differences

For the proposed transient Linefield property tray, recommend that the first press outside the tray and its owning hub closes it and consumes that complete pointer/contact sequence. It must not create a dot, begin a selection/move or activate an occluded tool on release. Drawing requires a fresh begin after dismissal. This avoids accidental marks during dismissal; the cost is an extra deliberate gesture when the user intends to adjust and immediately continue drawing. The alternative is Concepts-like nonmodal drawing-through with explicit close-only dismissal; that may support fast repeated adjustments but requires clear affordances and actual testing. The owner must choose the policy in the behavior packet. The study does not silently adopt either.

The permanent tool hub itself need not dismiss on a canvas press. It is not the separately documented squeeze-invoked palette: no observed permanent-hub behavior establishes squeeze placement, press/release semantics, dismissal or focus. Direct-touch hold-slide, contact transfer from a property into canvas and real pen interaction remain untested on this session.

In the approved scope, width/color describe the pen for subsequent strokes. Selecting artwork does not retarget these controls into a restyling command; Select requires no symmetric settings popup. If restyling is later approved, explicitly communicate “Selected stroke” versus “Pen,” announce the scope change accessibly and define transaction/Undo/restoration behavior before reusing controls. The observed single Undo is not sufficient to infer Concepts' complete model. The later return to Pen with width 8/smoothing 75 provides bounded evidence of separation in this sequence; it does not prove persistence across restart, all brush slots or every edit path.

A future live brush sample, if requested, should use the same shared artwork renderer and accepted style as real ink. It must be a bounded disposable scene, distinct from document strokes and selection: no document IDs, revision, history, autosave or export participation. The host owns its location, clipping, accessibility description and lifetime; Rust validates actual settings. A UI-only prototype cannot claim renderer fidelity. Do not reintroduce the observed huge canvas arc into Linefield's mockup or infer that it portrays physical size accurately.

Latest visual baseline and unresolved behavior

The owner's current exploratory direction contains five equal 72-degree outer tool sectors, with identical inner/outer radii and selection expressed by fill/icon contrast. Pen is at the top; clockwise illustrative glyphs are Eraser, Line, Shapes and Select. Icons are optically balanced as complete glyphs on sector bisectors, not centered by arbitrary SVG bounds. No tool-name labels, checkmarks, Undo/Redo, empty sectors or enlarged selected segment are shown. This does not prohibit accessible names, tooltips or labeled native fallback menus.

The small central color entry sits inside a property hub containing compact width, opacity and smoothing entries. Opening an entry highlights it and reveals one horizontal property tray:

  • Tray top/bottom align with the hub circle's top/bottom; tray height equals hub diameter.
  • Preserve the complete visible inner-circle outline even while the tray is open.
  • The tray overlays other tools. Approximately 50% background alpha is the owner's requested Linefield proposal, not a measured Concepts value; the observed Concepts alpha remains unknown. Text, icons, handles and control marks remain opaque. The tools are visible beneath it.
  • Earlier Linefield studies used a fully opaque thin-to-thick width indication; observed Concepts uses a thin constant-width slider track plus a separate artwork sample. Choose deliberately between them in the next visual packet. Opacity and width must not be mistaken for each other. Smoothing is a distinct labeled accessible property, not a different width or pressure control.
  • Opening/switching a tray never rearranges the five outer tools or shifts the canvas.

Critical proposed interaction improvement: visible tools beneath the translucent tray must not receive its pointer events. The tray owns its full bounds, including whitespace; underlying occluded tools are temporarily unavailable to pointer activation. A keyboard/AX alternative must remain coherent. This is a proposal for future review, not behavior established by images.

Remaining choice before detailed design review: retain a five-slot exploration only, approve the extra production tools, or redesign the same hierarchy for the two approved tools. Also resolve whether opacity/smoothing enter scope, property commit/cancel/history/restoration semantics, value units, discrete examples versus user presets, and full-color-picker behavior. Do not create a smoothing algorithm or property persistence contract through graphic design.

Responsive and native presentation

Treat window space, input capability, text size and platform styling independently. A narrow desktop window can need a compact presentation; a wide tablet window can support the full tray. Keep active tool, open property, selection, focus and viewport identity stable across adaptation.

At a screen edge, first choose a safe anchor or opposite tray expansion that does not rotate or reorder tool sectors. Do not move the wheel beneath an ongoing drag. If both directions fail, use the reviewed compact fallback instead of clipping targets. Orientation/resize invalidates stale pointer captures; full state continuity is subject to the shared interaction guard. The exact minimum footprint and target sizes need measured layouts, not raster estimates.

Inputs: visible tap/click entry remains mandatory. Keyboard activation uses native conventions, stable focus order and explicit acceptance rather than focus-to-select. Sliders expose a numeric alternative with locale-aware validation. Touch targets and separation are reviewed at actual display scale; pen hover never substitutes for discoverability. Pencil Pro squeeze is a future native adapter proposal, not a browser pressure heuristic or supported iPhone input. Supported non-squeeze styluses use visible controls; optional buttons require per-device mapping review.

Accessibility: every icon-only tool needs a localized name, accepted selected state and reason when unavailable. Property buttons expose value and expanded state; sliders expose range/value and keyboard increment. Focus remains visible over busy artwork and translucent surfaces. Use opaque backing for reduced transparency/contrast needs; do not fade control contents with the tray surface. A linear native/DOM alternative provides the same outcomes without requiring angular pointing. Screen-reader canvas editing itself remains a separate unverified problem.

Localization: retain shared trusted TypeScript catalogs and generated host resources. Native consumption remains pending. Design en/uk, pseudo-expanded, RTL and mixed-script states, numeric region variants and 200% text/browser zoom. Keep artwork/world coordinates and tool identity independent of UI direction; do not mirror the drawing or infer handedness from locale. A numeric field must preserve marked text and native shortcuts. Proficient Ukrainian terminology review is required; this designer does not certify translations. No in-app language switch is proposed.

Logical ownership and rendering recommendation

Retain the shared-canvas/host-chrome architecture. The radial selector's custom shape alone is insufficient reason for a shared Skia widget. No ABI, worker topology or schema is selected here.

A pure host wheel has the simplest coherent focus/AX/layout path and can survive a canvas surface failure. An all-Skia wheel would still require native accessibility and focus, duplicate hit geometry and complicate text scaling. A hybrid decorative Skia layer plus native targets is deferred until a concrete requirement demonstrates value; it is not needed merely to draw arcs. Mac native controls and web DOM controls can share semantic IDs/tokens while retaining behavior.
