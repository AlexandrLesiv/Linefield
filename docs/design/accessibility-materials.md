# Accessibility material policy

Status: browser Apple-preview control/container fallbacks implemented and tested in decision225 (WEB-GL01). Native mappings below are implementation requirements, not shipped support. Checked2026-10-17. Shared semantic theme colors do not replace native system preferences.

Decision 232 (2026-10-18) supersedes mandatory native material/visual styling. The platform-specific gallery appearances below describe existing evidence, not the future visual-system requirement. App-owned components use Linefield styling; accessibility preference integration and opaque fallbacks remain required wherever a reviewed design uses transparency.

When reduced transparency is requested, replace translucent material with an opaque semantic surface and remove backdrop blur. Keep foreground contrast, boundaries, focused state, control geometry and hit targets. Apply the change to visible parent toolbars and title backing as well as individual controls; an opaque button alone is insufficient. Apply at launch and on live system-setting changes without losing focus, text edits or navigation state. Increasing contrast and forced/system colors also take precedence over decorative material. Reduced motion is a separate preference: reducing transparency does not automatically disable all motion.

| Host | Platform mapping and acceptance |
| --- | --- |
| Web | `prefers-reduced-transparency: reduce`, independently `prefers-contrast: more` and `forced-colors: active`. Implemented on the Apple-preview compose/Back/iPad creation controls and enclosing toolbars/title backing. Browser reporting/support varies; no preference signal must not be presented as proof the user allows transparency. Test live media changes and parent backgrounds. |
| macOS/AppKit | Read `NSWorkspace.accessibilityDisplayShouldReduceTransparency`; observe `accessibilityDisplayOptionsDidChangeNotification`. Map translucent Linefield surfaces to opaque semantic backgrounds and retain increased-contrast behavior. Test actual System Settings while app is open. |
| iOS/iPadOS/UIKit | Read `UIAccessibility.isReduceTransparencyEnabled` and observe `reduceTransparencyStatusDidChangeNotification`. Let system controls respond natively; replace custom translucent surfaces with opaque equivalents. Test launch and runtime changes, keyboard, VoiceOver and both appearances on device. |
| Windows/WinUI | Native system backdrops should honor Windows preferences. Custom effects observe `UISettings.AdvancedEffectsEnabled`/`AdvancedEffectsEnabledChanged`; when false use opaque surfaces. Also preserve system high-contrast resources. Test Transparency effects and high contrast independently. |
| Android/ChromeOS | Use Linefield surfaces while preserving system theme/contrast behavior. Do not assume OEM transparency settings have one universal public API. During porting, verify supported SDK/device signals for custom effects; if a reliable signal is unavailable, use an opaque surface rather than depend on unobservable transparency preferences. Test representative supported devices. |
| Linux/GTK | Use Linefield surfaces with system high-contrast behavior and opaque fallbacks. Verify desktop/backend preference availability during porting; do not invent a universal reduce-transparency API. |
| watchOS/tvOS/visionOS and Wear/TV/XR | Adapt the Linefield visual system to native input, comfort and accessibility requirements; implement only supported signals after SDK feasibility. Validate each device/runtime separately; browser phone preview evidence does not certify these hosts. |

Acceptance IDs for future hosts: MAT-A01 launches with opaque material under the applicable preference; MAT-A02 applies live changes without losing interaction state; MAT-A03 covers parents/children and contrast/focus in both appearances; MAT-A04 distinguishes reduced motion and unavailable signals. Record exact OS/device/build and native execution, never count planned mappings as passes.
