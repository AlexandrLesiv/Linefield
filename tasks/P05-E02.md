### Owner-approved performance profile v1

Approval: “I approve performance profile v1, including the limits and early performance
checkpoint.” The exact proposal approved is recorded here; these are acceptance limits,
not claims of measured performance. Target responsive desktop drawing with budgets aimed
at60 Hz interaction on the same Mac/Chrome environment as E01. Headless evidence cannot
establish physical pen latency or visible frame rate. No foreground reservation is granted.

Six workload rows: each of the following at1024×768 and4096×2048 backing pixels:
repeated32-sample strokes; one65,537-sample stroke with continued drawing; and1,024 strokes
of64 samples including overlap. These are test workloads, never product limits. Cover warm
caches, cache-evicted reconstruction, Undo/Redo and pan/zoom.

| Metric | Approved limit |
| --- | --- |
| Input handler through Rust processing and returned-state copying | p95≤4 ms; maximum≤16 ms, including a full256-sample batch |
| Uninterrupted main-thread rendering work | p95≤8 ms short; ≤16 ms long/many |
| Longest application-owned main-thread task | Strictly below50 ms |
| Handler entry → submission of complete preview containing that input | p95≤33 ms short; ≤50 ms long/many; maximum≤100 ms |
| Accepted pan/zoom or Undo/Redo → complete current frame submitted and acknowledged | p95≤100 ms warm; ≤250 ms cold/evicted; maximum≤500 ms |
| Final pan update/release → fresh drawing available | ≤250 ms |

Submission/acknowledgement are browser-side milestones, not GPU completion or physical
presentation. Report browser event-delivery delay separately. Match input prefix and
content/mapping generations; never substitute background readiness for actual preview.

Method: release builds, five runs per workload and an untimed warm-up; collect at least100
observations per metric/cache condition before claiming a p95 pass. Report every run's
median/p95/worst; do not pool away slow runs. Keep screenshots, pixel comparisons and
recording outside timed intervals. Record exact build/browser/backend, dimensions, scale
and relevant host conditions; retain interrupted/invalid runs. Count superseded pan requests
and continuous busy periods so cancellation cannot hide slow rendering or starvation.

A same-machine p95 increase exceeding both15% and2 ms requires regression investigation;
absolute limits still apply. E01 comparison is valid only for genuinely matching workloads.
First accepted E02 build establishes the pen baseline; missing baseline is not a relative pass.
Memory targets remain soft; repeated navigation/rebuild must not retain obsolete resources.
No requirement to shrink Wasm heaps, no stroke quota, sample dropping or semantic weakening.

Early checkpoint: measure the minimum real pen/whole-path pipeline, especially long strokes
at both sizes, before completing the remaining E02 UI. If real performance misses, bring
the measured bottleneck and concrete alternatives to the owner. Do not silently relax limits,
split strokes, add workers/tiles or change renderer. Early feasibility measurements may
demonstrate failure before a complete acceptance matrix; incomplete evidence is not a pass.
